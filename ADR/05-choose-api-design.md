**ADR: 05-choose-api-disign - выбор передачи api**

**Дата:** 18 ноября 2026 г.

**Статус:** Принято

**Контекст:**

Для системы бронирования отелей необходимо определить единый подход к проектированию API, который обеспечит взаимодействие клиентских приложений с backend-системой, а также интеграцию с внешними сервисами. Необходимо учесть:

1. Простота интеграции с веб-приложениями.
2. Единообразие структуры запросов и ответов.
3. Безопасность взаимодействия между клиентом и сервером.
4. Масштабируемость и возможность дальнейшего расширения API.
5. Удобство документирования и тестирования.
6. Обратная совместимость при развитии API.

**Рассмотренные варианты:**

1. **REST API:** Архитектурный стиль взаимодействия между клиентом и сервером, основанный на HTTP-методах и ресурсах.
2. **GraphQL:** Язык запросов к API, позволяющий клиенту самостоятельно определять структуру необходимых данных. Обеспечивает гибкое получение данных.
3. **SOAP:** Протокол обмена структурированными сообщениями на основе XML.
4. **Гибридный подход:** Использование нескольких технологий API с OpenApi(Swagger) в зависимости от назначения взаимодействия: REST для клиентских приложений, WebSocket для чатов тех. поддержки.

**Решение:**

Выбран Гибридный подход.

**Обоснование:**

- **Простота интеграции:** REST API поддерживается практически всеми современными языками программирования, платформами и клиентскими приложениями.
- **Стандартизация:** Использование HTTP-методов и кодов ответов обеспечивает единообразие взаимодействия.
- **Масштабируемость:** структура позволяет расширять API без существенного изменения существующих запросов.
- **Документирование:** OpenAPI позволяет автоматически генерировать документацию и упрощает взаимодействие между frontend и backend-разработчиками.
- **Тестируемость:** REST API легко тестировать с помощью автоматизированных интеграционных тестов.
- **Удобство в подходе:** Исользование REST API для запросов, а WS для чатов.

**Недостатки решения:**

- **Избыточная передача данных:** В некоторых сценариях REST может возвращать больше данных, чем необходимо клиенту.
- **Количество запросов:** Для получения связанных ресурсов может потребоваться выполнение нескольких HTTP-запросов.

**Последствия:**

- Необходимо создать централизованную структуру REST API.
- Все API endpoints должны придерживаться единого соглашения по именованию ресурсов.
- Необходимо реализовать централизованную валидацию входящих запросов.
- Следует использовать единый формат HTTP-ответов и ошибок.
- Необходимо документировать API с помощью OpenAPI и Swagger.
- Необходимо предусмотреть защиту от CSRF-атак для запросов, использующих сессионные cookies.
